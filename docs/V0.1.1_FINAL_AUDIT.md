# V0.1.1 final implementation audit

This audit describes the implementation at commit
`cb447c84d972c717b573346544f84594e7134515`. The observed installation values
in the review request are acceptance evidence only; they are not copied into
runtime configuration or used as entity mappings.

## Existing processing path

1. The guided Config Flow and Options Flow store stable, user-editable equipment
   and temperature-source mappings. Runtime calculations consume those mappings;
   they do not contain installation entity IDs.
2. `RecorderReader` reads Home Assistant Recorder through its public APIs with
   `include_start_time_state=True`. Raw state transitions are primary. Long-term
   statistics are a fallback, and optional InfluxDB recovery is bounded and
   read-only.
3. Completed UTC hours and six-hour per-device checkpoints are persisted
   idempotently. Daily records reconcile checkpoint classification against the
   authoritative Recorder counter delta and retain residual evidence.
4. `time_weighted_temperature()` integrates validated values for the actual
   elapsed seconds until the next transition or explicit unavailable marker.
   Local-day boundaries are converted through the configured Home Assistant
   timezone, including 23-hour and 25-hour days.
5. SQLite contains one authoritative finalized row per local date plus hourly
   rows, checkpoints, mapping revisions, rejection audits and job evidence.
   History Today is composed in memory from completed hours and is not inserted
   as a finalized daily row.
6. Overview, History and CSV use the canonical energy contract. Missing values,
   known partial subtotals, assumed classifications, unallocated quantities and
   signed discrepancies are retained separately.

## Confirmed defects and implemented corrections

- Period allocation coverage is currently a count of fully good daily allocation
  rows. One partial device can therefore display 0% even when most elapsed time
  was classified. It must instead report elapsed classification coverage and
  expose processing completeness separately.
- When no representative temperature was previously selected, saving an
  unrelated Options Flow page can default to the first eligible source. This is
  an implicit configuration change.
- The period temperature headline can summarize any configured temperature
  source even when representative indoor/outdoor sources are not configured.
  Representative coverage must show `Not configured`, not a generic percentage.
- The representative selectors do not currently provide current value, unit,
  availability, last update and validation feedback in one explicit connection
  test.
- Mobile CSS preserves data through horizontal table scrolling, but controls,
  empty chart height, legends, pagination state and narrow summary presentation
  are not yet optimized for 360–430 CSS px.

The correction commit replaces binary allocation counts with elapsed classified
seconds per enabled equipment ID; removes representative-source auto-selection;
adds an explicit current value/unit/quality/timestamp preview; renders
unconfigured representatives as `Not configured`; and adds bounded pagination,
conditional period fields, touch-sized controls and compact mobile empty states.
Partial equipment keeps its independent meter, source, coverage, unknown and
residual evidence while incomplete categories remain unavailable.

## Configuration or live-data gaps, not confirmed calculation bugs

- The supplied Aurora partial values are consistent with incomplete power/mode
  coverage or a meter-to-classification residual. Repository code preserves the
  meter and residual, but the exact cause requires live entity history and the
  saved state mapping. It must not be guessed from rounded dashboard values.
- Missing representative temperature cards indicate missing/disabled selections
  or unavailable mapped entities. They do not prove Recorder history is absent.
- There is no configured thermal-energy measurement contract. Electrical demand
  response and area-normalized electrical demand can be reported, but delivered
  thermal energy and COP must remain unavailable until a compatible measured
  thermal source or an explicitly enabled estimation policy is configured.

## Existing behavior to preserve

- PV generation, self-use, import/export and household balance equations.
- Independent equipment meter totals and dynamic equipment IDs/names.
- Ecodan DHW versus space-heating separation and explicit assumed heating.
- AC confirmed, selected, estimated, dry/fan, standby and unknown categories.
- −55 °C / 155 °C sentinel rejection, configurable physical limits and temporal
  spike filtering.
- Recorder state-change semantics: an unchanged active state is not declared
  stale merely because no new state-change row was written. Carry-in timestamps
  and point-sample freshness evidence remain visible.
- Additive database migration, archive recovery and protected export behavior.

## Safe implementation plan

1. Correct coverage denominators and representative-source semantics first.
2. Add explicit representative-source validation/preview without changing saved
   selections automatically.
3. Improve allocation evidence and mobile presentation without reclassifying
   partial AC energy as confirmed.
4. Add measured electrical outdoor-response and normalized-demand reporting.
   Keep thermal/COP fields unavailable unless supported by configured evidence.
5. Extend deterministic regression and Home Assistant runtime tests before
   updating the draft pull request.

The electrical response profile follows this plan: complete daily heat-pump and
AC space-heating allocations are combined, paired only with the explicitly
selected outdoor source, binned by outdoor temperature and normalized by the
configured floor area. It labels thermal output, COP and design-day output as
unavailable when their independent evidence is absent.
