### Temperature-repair query and write audit

The corrected collector uses one bounded Recorder history call and requests one
long-term-statistics batch only for sources whose raw state history has zero
validated elapsed coverage. The important before/after difference is scope,
coverage-based fallback and pre-query skipping:

| Range/state | Former collector | Corrected collector |
|---|---:|---:|
| One day needing repair | 2 Recorder calls containing every enabled equipment, site and temperature entity | 1 temperature-only history call; +1 statistics call only when raw validated coverage is zero |
| Two-day startup maximum | 4 broad Recorder calls, awaited before later recovery | 0–4 temperature-only calls in isolated bounded background work; normally 2 when carry states are valid |
| 31-day explicit maximum | 62 broad Recorder calls | 0–62 temperature-only calls; normally 31 when carry states are valid; complete source/day combinations make no calls |
| Already complete range | 2 calls per day | 0 calls |

Optional InfluxDB fallback remains bounded, read-only and source-specific. The
repair does not perform a full-day energy calculation, create daily records or
write Recorder/InfluxDB. Normal collection retains its existing broad query path;
only diagnostics and temperature repair use the lean collector.

### Atomic merge guarantees

- The latest row is read after `BEGIN IMMEDIATE`; a checksum predicate guards the
  update and locked-database retries are bounded.
- Candidate UTC boundaries and entity provenance must match the stored interval
  and historical source meaning.
- Complete higher-quality evidence cannot be replaced by lower-quality or
  shorter evidence. Identical retry changes no timestamp or revision.
- Daily repair increments the existing revision convention with reason
  `temperature_history_repair`; hourly repair keeps the established hourly
  no-revision convention.
- Allocation rows and rejection audits for equipment or unchanged temperature
  sources are not rebuilt. Transaction failure rolls back payload, checksum,
  revision and changed-source rejection audit together.

## Root-cause findings

### Confirmed: Options Flow could lose queued mappings

Affected functions: `_Wizard._load()`, `_equipment_step()`,
`async_step_temperatures()` and `OptionsFlow._finish()` in `config_wizard.py`.

The edit UI moved existing records out of the working collection into pending
queues. Submitting `configure = false` after queue initialization advanced to the
next page without restoring the pending records. The disable path also rebuilt a
record from submitted form values and unnecessarily required live-source
validation. A validation error did reinsert the current item; cancellation did
not modify the stored config entry because Home Assistant had not called
`_finish()`. Those two paths were risks but were not the data-loss defect.

The flow now edits a deep-copied draft. Skip restores the complete queue,
explicit disable retains the original mapping and stable ID, remove remains the
only deletion action, and `_finish()` deep-copies the validated result. Unchanged
mapping data retains its original `mapping_effective_at`. Runtime tests cover one
heat pump, three AC units, three temperature sources, representative selections,
site mappings, skip, disable, remove and validation failure.

### Confirmed: absent classification coverage could mean complete

Affected functions: `canonical_energy()`, `kind_complete()`,
`combine_interval_records()` and `daily_coverage()` in `analytics.py`.

The compatibility condition accepted a missing `coverage_percent` as full
coverage. Legacy rows without duration metadata could therefore expose complete
category totals. Coverage is now reconstructed only from explicit
`covered_seconds / period_seconds` or an explicit percentage. Otherwise it is
unknown. The independent meter total and known category subtotals remain
readable, while complete heating/cooling/DHW fields remain unavailable. Period
coverage exposes both exact coverage (nullable) and a known lower bound.

### Confirmed: date coverage used calendar-row counts

`daily_coverage()` previously documented elapsed-duration coverage but computed
date coverage from present-day counts. It now uses UTC elapsed seconds between
local day boundaries. Full dates retain 23/24/25-hour denominators. A partial
current day contributes only processed elapsed seconds to availability but keeps
the full local day as the date-availability denominator. Meter and allocation
coverage retain the completed-hour cutoff as their processing scope.

### Confirmed risk: response-profile qualification was too permissive

The initial response API silently omitted rejected days, accepted any numerical
outdoor mean, and the frontend allowed a fitted result after five points without
an outdoor-span requirement. The backend now returns every daily candidate as
`validated` or `excluded`, with reasons and provenance. Default qualification
requires 95% representative-outdoor coverage, complete enabled-device heating
classification, a known reconciled HVAC total, a valid finalized date and floor
area. Regression display requires at least 10 validated days, an 8 °C observed
span and R² of at least 0.5. Excluded evidence remains visible. The UI does not
claim a physical balance point, design-day output, thermal output or COP.

### Confirmed: partial device chart could look like zero

`equipmentComparison()` converted nullable category values to zero before bar
rendering. It now plots only classification-complete devices. Partial device
meters, known subtotals, unknown energy, residual, source and coverage remain in
the evidence table and are explicitly named below the chart.

### Not a calculation defect: PV/grid equations

The existing equations were correct and measured household electricity remained
authoritative. Tests now cover zero PV, missing PV, missing import, impossible
export, negative production and independently rounded values. Reconstructed
household electricity and its signed discrepancy remain validation evidence; they
do not replace the measured counter.

### Schema V4 storage recovery

Independent review found that large temperature audit arrays remained duplicated
inside record JSON. Schema V4 transactionally extracts per-source summaries and
hourly rejection evidence into normalized tables while preserving the hydrated
logical record contract. Daily energy, allocations, checkpoints, job runs,
mapping revisions and revision history are not rebuilt. Conversion now uses
bounded keyset batches and startup never runs `VACUUM`. Forced DDL, conversion,
disk-full and version-bump failures prove that the prior inline payload and schema
version remain readable and retryable; V1/V2/V3 upgrades and V4 reopen are tested,
including thousands of daily/hourly records. Current-day partial rows remain in
memory rather than finalized history.

### Confirmed: no temperature-only historical recovery path

The October 29 symptoms are consistent with hourly/daily energy rows having been
persisted before the corrected representative mapping could contribute a valid
temperature summary. Normal hourly recovery revisited only absent/poor recent
rows and daily catch-up rebuilt absent dates; neither repaired a valid energy row
whose temperature payload alone was absent. The cards and response chart then
correctly received no validated temperatures from SQLite.

The correction records collection evidence at the Recorder boundary and exposes
an administrator diagnostic for every later stage. Startup repairs temperature
summaries only for the latest two dates; an explicit operation covers up to 31
days. Merge policy preserves all electricity/allocation fields and any existing
temperature summary with equal or greater valid duration. No interval is bridged.
Because this repository session has no access to the user's live Home Assistant
Recorder or config entry, the exact source-specific October 29 failing stage must
be confirmed by the new diagnostic on the backed-up instance; it is not inferred
from the screenshots.

## Data compatibility

- The additive, transactional schema version advances from V3 to V4.
- Existing V1–V3 SQLite databases migrate automatically after integrity check;
  failed V4 conversion does not bump the version.
- Daily rows, hourly rows, six-hour checkpoints and rejection audits are retained.
- Equipment and source IDs are retained unless the user explicitly removes an item.
- Existing config-entry data/options and InfluxDB credentials are preserved.
- Mapping revisions are retained; unrelated saves do not create a false mapping
  effective date.
- Downgrading writers to V3 after migration is unsupported; take the protected
  administrator backup before installation or rollback.

## Final quality-recovery evidence

- `daily_coverage()` no longer treats the stored row label as current truth.
  It derives date, household-meter, enabled-device allocation and selected
  representative-temperature layers and preserves the old label only as
  provenance.
- A repaired day becomes derived `good` only when every required layer is
  evidenced. Missing representative outdoor coverage remains `partial`; legacy
  allocation rows without elapsed coverage are `unknown`, never implicitly good.
- Both heating-response views consume the same backend candidates. Admission
  requires a finalized day, the selected measured outdoor source, at least 95%
  valid outdoor duration, complete enabled-device classification, reconciliation
  within 0.05 kWh and floor area. Regression display additionally requires 10
  admitted days, 8 °C observed span and R² ≥ 0.5.
- Repair responses now report bounded Recorder/Influx query counts and peak
  normalized samples per day. CI exercises both 2-day and 31-day ranges.
