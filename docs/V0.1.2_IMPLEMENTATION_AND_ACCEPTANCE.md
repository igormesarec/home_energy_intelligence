# Home Energy Intelligence V0.1.2 implementation and acceptance

## Scope and evidence boundary

V0.1.2 repairs independent temperature history, current-cutoff HVAC presentation, quality reporting, energy-season controls and frontend release invalidation. It does not add thermal output, COP or forecasting. Development and automated tests use fixtures/mocks only; they are not evidence that the production Home Assistant installation was changed or validated.

The root-cause analysis is in `V0_1_2_ROOT_CAUSE_MATRIX.md`.

## Schema V5

The migration is additive and transactional:

- `temperature_history_records` stores hourly or completed-day summaries independently of energy rows.
- `temperature_mapping_events` stores chronological configuration occurrences. An A→B→A sequence creates three events.
- `temperature_mapping_attestations` stores an administrator's explicit, bounded entity/attribute/role assertion.
- `temperature_backfill_jobs` stores the inclusive date range, next-date cursor, dry-run/status/cancellation state, counters and skip reasons.

No migration statement updates `daily_records`, `hourly_records`, `checkpoints`, `allocations`, `revisions`, PV/grid fields or rejection audits. Startup does not run `VACUUM`. The version changes only after the transaction succeeds. Tests cover injected failure rollback, low free-space deferral, lock handling, idempotent reopen and exact energy/checkpoint payload/checksum preservation.

## Backfill behavior

The administrator workflow separates three actions:

1. **Diagnose** performs bounded reads and reports live identity/unit/attribute state, Recorder evidence, validated duration, independent/energy history, mapping eligibility, likely query count and missing reasons.
2. **Repair existing summaries** retains the V0.1.1 source-aware merge into existing energy rows.
3. **Preview/Start temperature-only backfill** processes 1–31 inclusive local dates, creates no energy row, and persists only validated temperature summaries.

Each day is queried independently to bound memory. The raw Recorder query includes its carry-in state. UTC hourly boundaries preserve repeated/missing DST hours. Invalid units, sentinels, physical outliers, temporal spikes, stale point samples and explicit unavailable/unknown periods remain rejected or uncovered. A shared physical entity is queried once while its stable logical source IDs remain separate.

Jobs save the next-day cursor after each day, resume queued/running/interrupted work after integration setup, check cancellation between days, and use interval/source primary keys plus evidence-improving merges for idempotence. A completed retry reports unchanged rows. A job with zero recoverable rows and outstanding gaps reports **No records recovered — action required** rather than success.

Historical identity is accepted only from a mapping event that covers the exact interval or an explicit bounded attestation. Previewing an attestation does not persist it; starting an attested job does. Mapping changes inside an interval are skipped with an explicit reason rather than guessed.

## Backup, update and rollback

Before installation:

1. Use the administrator-only protected database export or stop Home Assistant and copy `<config>/.storage/home_energy_intelligence/home_energy_intelligence.sqlite3` together with any `-wal`/`-shm` companions.
2. Record the integration options and representative source selections. Do not delete/recreate the config entry.
3. Install V0.1.2 through HACS and restart Home Assistant once.
4. Confirm Settings reports schema 5 and that `/home-energy-intelligence` loads the 0.1.2 content-hashed panel.

If migration or startup fails, retain the database and logs. Free the reported disk space or remove the lock, then retry. For rollback to a V0.1.1/V4 writer, stop Home Assistant, restore the complete backed-up V4 database set, restore the earlier integration files, and restart. Do not point an older writer at the migrated V5 database.

1. Confirm the saved 170 m² floor area, Europe/Berlin timezone, all equipment IDs, PV/grid mappings and representative source IDs are unchanged.
2. Confirm the panel JavaScript request includes `v=0.1.2-<content hash>` after the HACS update and restart in desktop Chrome and Android Home Assistant/browser. Do not clear or recreate the integration.
3. Diagnose September 29–October 30, 2026. Record raw rows, validated seconds, energy rows, independent temperature rows, mapping decisions, query count and recoverable/blocked intervals.
4. Preview no more than 31 days. Review every mapping block. Use attestation only with installation records proving the exact historical entity/attribute/role.
5. Start one bounded range. Verify progress/cancellation, restart during a backed-up test job, resume, and repeat the same range. The repeat must insert/update zero additional summaries.
6. Compare electricity, PV, grid, HVAC allocation and checkpoint checksums/balances before and after. They must be unchanged.
7. Verify indoor/outdoor/DHW/flow cards and History acquire only validated time-weighted evidence, retain gaps and rejection details, and never substitute flow water for outdoor air.
8. At a completed-hour cutoff, verify household and confirmed/selected/estimated HVAC values against source meters. The known subtotal must be the main value, labelled provisional through the Home Assistant-local cutoff; yesterday same-cutoff and full-day totals remain separate.
9. Verify heating-response points appear only where a completed daily energy allocation and the selected measured outdoor source meet the configured coverage rule. Temperature-only dates must remain excluded from heating response.
10. Exercise the season controls in English and Slovenian, save without changes, and confirm the floor area and all mappings remain intact.
11. Check long tables, controls and status text at 360–430 px widths and on desktop. Capture screenshots as real-installation evidence.
